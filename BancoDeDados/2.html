O Paradigma Relacional: Tabelas, Linhas e Colunas

E. F. Codd (1970)

Criado por Edgar F. Codd na IBM, o Modelo Relacional fundamenta-se na teoria matemática dos conjuntos. Os dados são organizados em estruturas bidimensionais chamadas Relações (Tabelas).

Relação (Tabela): O conjunto de dados que representa uma entidade. Table
Tupla (Linha / Registro): Uma ocorrência factual única dentro da relação. Row / Record
Atributo (Coluna / Campo): A característica descritiva com domínio rígido. Column

O Escudo das Transações: Propriedades ACID

Garantia Crítica

Uma transação é um conjunto de operações executadas como um bloco único. O modelo relacional garante as 4 letras do acrônimo ACID:

A

Atomicidade

"Tudo ou nada". Ou todas as operações da transação são confirmadas (COMMIT), ou nenhuma é gravada (ROLLBACK).

Sem estados parciais no banco.
C

Consistência

O banco sai de um estado válido e chega a outro estado válido, respeitando todas as regras de integridade e restrições.

Nenhuma regra quebrada.
I

Isolamento

Transações concorrentes não interferem umas nas outras. O resultado é idêntico a executá-las em sequência.

Evita leituras "sujas" ou fantasmas.
D

Durabilidade

Uma vez finalizada, a gravação é permanente em disco físico ou réplicas, sobrevivendo a quedas de energia e panes.

Dados seguros mesmo com crash.
💳 Exemplo Clássico: Se R$ 500 saem da conta de Alice mas a conexão cai antes de creditar na conta de Bob, a Atomicidade desfaz o débito instantaneamente.
Rollback Automático

A Revolução NoSQL: Not Only SQL

Escalabilidade & Flexibilidade

Com o nascimento de gigantes como Google, Amazon e Facebook nos anos 2000, o volume de dados explodiu e surgiram demandas que os bancos relacionais tradicionais tinham dificuldade de atender com baixo custo.

1. Escalabilidade Horizontal (Scale-Out) Em vez de comprar um supercomputador milionário (escala vertical), o NoSQL distribui petabytes de dados em dezenas de servidores comuns em cluster.
2. Esquema Flexível (Schema-less / Dynamic) Capacidade de guardar registros com formatos diferentes sem precisar recriar ou alterar a estrutura da tabela inteira.
3. Alta Velocidade de Escrita Projetados para suportar milhões de cliques por segundo de usuários globais conectados.
Como o Sistema Cresce?
🖥️ ➔ 🏢 Escala Vertical (SQL)

Colocar mais RAM, CPU e SSD no mesmo servidor. Alto custo limite.

💻 ➔ 💻 💻 💻 Escala Horizontal (NoSQL)

Adicionar mais nós comuns trabalhando em equipe. Escalabilidade infinita.

💡 Atenção: NoSQL não significa "sem SQL", mas sim "Not Only SQL" (Não Apenas SQL). Ambos coexistem no mercado moderno!

Documentos e Chave-Valor

MongoDB & Redis
FAMÍLIA 1 JSON / BSON

Banco Baseado em Documentos

Armazena os dados em documentos estruturados (como JSON). Cada documento pode ter campos diferentes, suportando listas e objetos aninhados.

// Exemplo de Documento no MongoDB
{
  "id": 101,
  "nome": "Carlos Silva",
  "emails": ["carlos@email.com", "c.silva@corp.com"],
  "preferencias": { "tema": "escuro", "notif": true }
}
Casos de Uso: Catálogo de e-commerce, blogs, CMS. MongoDB, CouchDB
FAMÍLIA 2 Memória RAM / Cache

Banco Chave-Valor (Key-Value)

O modelo mais simples e ultra veloz. Cada registro é formado por uma chave única que aponta para um valor arbitrário.

"sessao:usr_8921" → "token_auth_xyz123"
"carrinho:usr_8921" → [item_12, item_44]
"views:post_304" → 14.920
Casos de Uso: Cache em milissegundos, logins, carrinhos. Redis, DynamoDB

Bancos de Grafos e Família de Colunas

Neo4j & Cassandra
FAMÍLIA 3 Nós & Arestas

Banco de Grafos

Focado nas relações complexas entre elementos. As entidades são Nós (Nodes) e as conexões entre elas são Arestas (Edges) com propriedades próprias.

(Ana) ──[AMIGA_DE]──▶ (Bia)
Bia ──[COMPROU]──▶ Livro de Python ◀──[CURTIU]── Ana
Casos de Uso: Redes sociais, antifraude, rotas, recomendação. Neo4j, Amazon Neptune
FAMÍLIA 4 Wide-Column

Banco Colunar (Wide-Column)

Em vez de salvar linha por linha, armazena os dados agrupando famílias de colunas juntas em disco. Permite compactação impressionante e consultas analíticas velozes sobre petabytes.

sensor_id_01: timestamp_1=24.5C, timestamp_2=24.8C
sensor_id_02: timestamp_1=80.1%, timestamp_2=79.9%
Casos de Uso: Big Data, IoT, séries temporais e telemetria. Cassandra, ScyllaDB, HBase

A Jornada da Modelagem: Os 3 Níveis Essenciais

Arquitetura ANSI/SPARC

Nenhum engenheiro de software experiente cria tabelas direto no terminal. O projeto de banco de dados passa obrigatoriamente por 3 níveis de abstração progressivos:

NÍVEL 1

Modelo Conceitual

Focado nas regras de negócio e na visão do usuário. Independente de qualquer software, tecnologia ou SGBD.

Ferramenta: Modelo Entidade-Relacionamento (MER / DER).
Público: Clientes, analistas e gestores.
NÍVEL 2

Modelo Lógico

Adapta o modelo conceitual ao paradigma escolhido (ex: Relacional). Define tabelas, colunas, chaves primárias e estrangeiras.

CLIENTES (id_cli [PK], nome, cidade)
Público: Desenvolvedores e arquitetos.
NÍVEL 3

Modelo Físico

A implementação no SGBD específico (Postgres, Oracle, MySQL). Comandos DDL, tipos exatos, índices e armazenamento em disco.

CREATE TABLE clientes (...);
Público: DBAs e Engenheiros de Dados.

Nível Conceitual: Modelo Entidade-Relacionamento

Peter Chen (1976)

O MER (Modelo Entidade-Relacionamento) é a representação gráfica do mundo real através de símbolos padronizados.

RET
Entidade (Retângulo) O "objeto" do mundo real sobre o qual guardamos dados. Ex: CLIENTE, PRODUTO.
OVAL
Atributo (Elipse / Círculo) As propriedades que caracterizam a entidade. Ex: nome, preco, cpf.
LOS
Relacionamento (Losango) A ação ou associação que une entidades. Ex: REALIZA, CONTÉM.
Esquema Gráfico Simplificado
CLIENTE
REALIZA
PEDIDO
Lê-se: "Um Cliente REALIZA um Pedido." Mas quantos pedidos um cliente pode fazer? Isso nos leva à Cardinalidade!

Cardinalidades no MER: 1:1, 1:N e N:N

Mapeamento Real
1 : 1

Um para Um

Cada ocorrência de A se relaciona com no máximo uma de B, e vice-versa.

Exemplo: Um Cidadão possui um único Título de Eleitor; cada título pertence a um único cidadão.
Frequente em dados confidenciais separados.
1 : N (ou 1:*)

Um para Muitos

Uma ocorrência de A se relaciona com várias de B, mas cada ocorrência de B pertence a apenas uma de A.

Exemplo: Um Cliente faz muitos Pedidos; mas cada Pedido pertence a apenas um Cliente.
O relacionamento mais comum nos negócios!
N : N (ou * : *)

Muitos para Muitos

Uma ocorrência de A se relaciona com várias de B, e uma ocorrência de B se relaciona com várias de A.

Exemplo: Um Aluno cursa várias Disciplinas; cada Disciplina possui vários Alunos.
⚠️ Requer tratamento especial no Modelo Lógico!

Chaves e Restrições de Integridade (Constraints)

Regras Inegociáveis
As Chaves Fundamentais
🔑 Primary Key (PK) - Chave Primária

Identificador único obrigatório (NOT NULL + UNIQUE) da tupla. Garante que nenhuma linha seja idêntica a outra.

🔗 Foreign Key (FK) - Chave Estrangeira

Aponta para a PK de outra tabela. Assegura a Integridade Referencial: impede registrar um pedido para um cliente inexistente!

Restrições Adicionais (Constraints)
NOT NULL Impede que o campo fique vazio (obrigatório).
UNIQUE Garante valores únicos (ex: CPF, e-mail).
CHECK Valida condições lógicas: idade >= 18 ou preco > 0.
DEFAULT Atribui valor padrão automático se nada for informado.

Nível Físico: DDL e Implementação no SGBD

Data Definition Language

O Modelo Físico expressa as decisões técnicas finais no dialeto específico do SGBD escolhido (PostgreSQL, MySQL, SQL Server):

1. Especificação Rigorosa de Tipos: Substituição de conceitos abstratos por tipos de dados exatos da máquina: INT, VARCHAR(120), NUMERIC(10,2), TIMESTAMP.
2. Criação de Índices (INDEX): Estruturas em árvore B-Tree para permitir que o SGBD encontre um cliente por CPF em frações de milissegundo.
3. Organização em Disco & Particionamento: Como os arquivos .mdf ou blocos de dados serão fisicamente distribuídos nos discos SSD.
-- Script DDL no PostgreSQL SQL Físico
CREATE TABLE clientes (
  id_cliente SERIAL PRIMARY KEY,
  nome_completo VARCHAR(100) NOT NULL,
  cpf CHAR(11) UNIQUE NOT NULL,
  data_cadastro TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_clientes_cpf ON clientes(cpf);

Por que Normalizar? O Pesadelo das Anomalias

Prevenção de Falhas

A Normalização é o método formal de análise de esquemas de tabelas para eliminar redundâncias desnecessárias e proteger o banco contra as 3 anomalias operacionais mortais:

1

Anomalia de Inserção

Impossibilidade de registrar um novo dado sem cadastrar obrigatoriamente outro dado ainda inexistente.

Ex: Não conseguir cadastrar um novo curso na faculdade porque nenhum aluno se matriculou nele ainda.
2

Anomalia de Exclusão

Ao apagar um registro desejado, perder acidentalmente e sem querer outros dados cruciais da empresa.

Ex: Demitir o único vendedor de uma filial e, ao deletar a linha dele, apagar os dados da filial inteira.
3

Anomalia de Alteração

O mesmo dado está repetido em 50 linhas; você atualiza em 10 e esquece em 40, criando contradições graves.

Ex: Mudar o preço do "Mouse" em uma venda passada e o sistema passar a cobrar dois preços diferentes.
🛡️ O Remédio: As Formas Normais (1FN, 2FN e 3FN), aplicadas de forma sequencial e acumulativa!

1ª Forma Normal (1FN): Atomicidade Total

Valores Indivisíveis
Regra da 1FN: Uma tabela está na 1FN se, e somente se, todos os seus atributos contiverem apenas valores atômicos (indivisíveis), sem repetições de campos multivalorados e sem atributos compostos. Além disso, deve possuir uma Chave Primária identificada.
❌ VIOLA A 1FN (Campos Misturados e Repetidos) Erro
Carlos Mendes
Telefones: (11) 9876-1111, (11) 9999-2222 (Multivalorado!)
Endereço: Av. Paulista, 1000 - SP (Composto não atômico!)
✅ NA 1ª FORMA NORMAL (Valores Atômicos) 1FN OK
Tabela Clientes:
id_cli (PK) | nome | logradouro | numero | uf
101 | Carlos Mendes | Av. Paulista | 1000 | SP
Tabela Telefones_Cliente (1:N):
id_tel (PK) | id_cli (FK) | telefone
1 | 101 | (11) 9876-1111
2 | 101 | (11) 9999-2222

2ª Forma Normal (2FN): Eliminação de Dependência Parcial

Dependência Total
Regra da 2FN: A tabela deve estar na 1FN E nenhum atributo não-chave pode depender apenas de parte de uma Chave Primária Composta. Toda coluna descritiva deve depender da chave primária por inteiro.
❌ VIOLA A 2FN (Dependência Parcial da Chave) Erro
Tabela Item_Pedido:
PK Composta: (id_pedido, id_produto)

• quantidade (depende do pedido E do produto OK)
• nome_produto (ERRO: depende apenas de id_produto!)
✅ NA 2ª FORMA NORMAL (Separada em Duas Tabelas) 2FN OK
Tabela Item_Pedido:
id_pedido (PK, FK) | id_produto (PK, FK) | quantidade
Tabela Produtos:
id_produto (PK) | nome_produto | preco_unitario
💡 Dica Prática: Se uma tabela tem uma Chave Primária simples (apenas 1 coluna) e já está na 1FN, ela automaticamente já está na 2FN!

3ª Forma Normal (3FN): Sem Dependências Transitivas

O Padrão Ouro
Regra da 3FN: A tabela deve estar na 2FN E nenhum atributo não-chave pode depender de outro atributo não-chave.
Lema clássico: "O atributo deve depender da chave, de toda a chave e de nada além da chave!"
❌ VIOLA A 3FN (Dependência Transitiva) Erro
Tabela Funcionarios:
id_func (PK) | nome | id_departamento | nome_departamento

O nome_departamento depende de id_departamento (que NÃO é a chave da tabela!).
✅ NA 3ª FORMA NORMAL (Transição Isolada) 3FN OK
Tabela Funcionarios:
id_func (PK) | nome | id_departamento (FK)
Tabela Departamentos:
id_departamento (PK) | nome_departamento | localizacao
✨ Se o nome do departamento mudar de "TI" para "Tecnologia", você altera em uma única linha em vez de alterar em 500 funcionários.

Desnormalização Consciente: Quando Quebrar Regras?

Prática Avançada

Tabelas perfeitamente normalizadas na 3FN exigem muitas operações de JOIN para reunir os dados. Em sistemas com petabytes de dados e dashboards analíticos pesados, isso pode ficar lento.

O que é Desnormalizar de modo Consciente?

É a introdução controlada de redundância com o objetivo explícito de acelerar leituras analíticas ou salvar "fotos imutáveis do passado".

Exemplo 1: Foto Histórica da Venda Salvar o endereço de entrega e o preço dentro do pedido evita que um reajuste futuro altere o extrato fiscal do passado!
Exemplo 2: Data Warehouse & BI Tabelas Fato e Dimensões agrupadas para gerar relatórios anuais em segundos.
Onde usar cada abordagem?
OLTP (Transacional / Dia a Dia) Compras, cadastros, transferências. Normalizado (3FN Obrigatório)
OLAP (Analítico / BI / Dashboards) Mineração de dados, relatórios gerenciais históricos. Desnormalizado com Critério

Gabarito Oficial e Guia Pedagógico

Questão 1: Propriedades ACID

Resposta Correta: A Atomicidade. Ela garante que uma transação seja indivisível: se houver falha no meio do processo, todas as operações anteriores são desfeitas (ROLLBACK).

Questão 2: Bancos NoSQL de Grafos

Resposta Correta: São ideais para representar conexões ricas e caminhos complexos (como redes sociais e detecção de fraudes), utilizando nós e arestas com propriedades (ex: Neo4j).

Questão 3: Resolução de Relacionamento N:N no Modelo Lógico

Resposta Correta: Criar uma tabela associativa (intermediária) que recebe as Chaves Primárias das duas tabelas originais como Chaves Estrangeiras (FK).

Questão 4: Regra da 1ª Forma Normal (1FN)

Resposta Correta: Exige que todos os atributos contenham valores atômicos indivisíveis, proibindo repetições de listas na mesma célula (como telefones separados por vírgula) e atributos compostos não decompostos.

Questão 5: Regra da 3ª Forma Normal (3FN)

Resposta Correta: A tabela deve estar na 2FN e não pode conter dependência transitiva (isto é, nenhum atributo não-chave pode depender funcionalmente de outro atributo não-chave).

Toda tabela precisa de PK: Nunca crie uma tabela sem Chave Primária definida.
3.
Integridade Referencial sempre: Use FKs para impedir o nascimento de dados órfãos.
4.
Normalização como padrão: Alcance a 3FN em todos os sistemas de transação (OLTP).
5.
Desnormalize apenas com métricas: Somente em relatórios analíticos pesados e comprovados.
6.
Escolha a ferramenta certa: Use NoSQL para volume, cache e flexibilidade; use SQL para ACID.
7.
Segurança & Tipagem Rígida: Restrições (CHECK, NOT NULL) no banco são a última linha de defesa contra bugs do sistema!
