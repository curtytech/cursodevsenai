Segurança em Banco de Dados: O Cenário Crítico

Alto Risco

Os bancos de dados corporativos são o cofre digital de qualquer organização: guardam segredos industriais, dados de cartões, senhas e prontuários médicos.

1. Vazamentos de Dados & Multas da LGPD Multas de até 2% do faturamento (limitadas a R$ 50 milhões por infração) e perda irreversível da confiança do cliente.
2. Ataques de Ransomware & Sequestro Cibercriminosos criptografam os arquivos de dados físicos do SGBD e exigem resgate milionário em criptomoedas.
3. Ameaças Internas (*Insider Threats*) Funcionários descontentes ou mal treinados com acesso excessivo deletando ou vazando informações estratégicas.
A Estratégia de Defesa em Camadas (*Defense in Depth*)
Camada 1: Rede & Firewall Bloqueio de Portas Externas
Camada 2: Autenticação & RBAC Identidade + Menor Privilégio
Camada 3: Criptografia (TLS + TDE) Dados ilegíveis em trânsito e repouso
Camada 4: Backup Imutável Garantia final de sobrevivência
🛡️ Segurança em banco de dados não é uma ferramenta única, mas um processo contínuo em camadas!

Controle de Acesso: O Modelo RBAC

Role-Based Access Control
1. Autenticação (Quem é você?) Validação de identidade via senhas fortes, chaves SSH, certificados digitais ou integração com Active Directory / LDAP.
2. Autorização (O que você pode fazer?) Definição exata de quais tabelas, views e procedimentos aquele usuário autenticado pode ler ou modificar.
⭐ Princípio do Menor Privilégio (*Least Privilege*): Cada usuário ou serviço deve ter apenas as permissões estritamente indispensáveis para sua função, nem mais, nem menos.
Como funciona o RBAC na Prática:
Role (Papel): 'role_atendimento' Permissões: SELECT em vw_clientes_basico, INSERT em chamados.
Role (Papel): 'role_financeiro' Permissões: SELECT e UPDATE em faturas e contas_a_pagar.
-- No SQL atribuímos a Role aos usuários:
CREATE ROLE role_atendimento;
GRANT SELECT ON vw_clientes_basico TO role_atendimento;
GRANT role_atendimento TO usuario_joao;

Criptografia: Em Trânsito, Em Repouso e Mascaramento

TLS & TDE
EM TRÂNSITO

Criptografia em Trânsito (TLS/SSL)

Protege os dados enquanto eles viajam pelos cabos de rede e internet entre a aplicação e o servidor de banco.

Evita interceptações tipo Man-in-the-Middle e espionagem de rede (*Sniffing*).
EM REPOUSO

Criptografia em Repouso (TDE)

*Transparent Data Encryption*. Os arquivos .mdf ou blocos no disco SSD são criptografados com algoritmos como AES-256.

Se um invasor roubar o disco físico ou o arquivo de backup, ele não consegue ler nada sem a chave mestra.
MASCARAMENTO

Mascaramento Dinâmico (DDM)

Ofusca dados sensíveis em tempo real na tela de acordo com o nível do usuário, sem alterar o valor original gravado no disco.

Ex: CPF: ***.456.789-**
Cartão: ****-****-****-1234

Módulo 5.1 • Vulnerabilidade Nº 1 da Web

A Ameaça do SQL Injection (SQLi) e a Blindagem

OWASP Top 10

O SQL Injection ocorre quando um sistema junta (concatena) comandos SQL com textos digitados diretamente pelo usuário sem nenhuma validação prévia.

Exemplo de Entrada Maliciosa no Campo Usuário: ' OR '1'='1' --

Como '1'='1' é sempre verdadeiro, a query ignora a senha e o invasor faz login como administrador do sistema!

🛡️ A Solução Definitiva: Prepared Statements (Queries Parametrizadas)
O SGBD compila o código SQL primeiro e trata o texto do usuário estritamente como dado puro, nunca como código executável!
-- O Erro Mortal vs A Blindagem
-- ❌ VULNERÁVEL (Concatenação de String):
query = "SELECT * FROM users WHERE login = '" + campo_user + "' AND pass = '" + campo_pass + "'";

-- ✅ BLINDADO (Prepared Statement com Parâmetros ?):
query = "SELECT * FROM users WHERE login = ? AND pass = ?";
stmt = db.prepare(query);
stmt.bind(1, campo_user);
stmt.bind(2, campo_pass);
stmt.execute(); -- 100% Imune a SQLi!

A Estratégia de Backup: A Regra de Ouro 3-2-1

Sobrevivência de Dados

Ter uma cópia salva no mesmo servidor não é backup. A indústria de tecnologia adota como padrão a Regra 3-2-1 para garantir que os dados sobrevivam a incêndios, inundações e ataques cibernéticos:

3

3 Cópias dos Dados

A cópia de produção principal (onde o sistema roda) + 2 cópias de backup independentes.

Produção + Backup A + Backup B
2

2 Mídias Diferentes

Armazenadas em tecnologias distintas: por exemplo, um storage NAS local + armazenamento em Nuvem (Object Storage).

Evita falha no mesmo tipo de hardware
1

1 Cópia Fora do Local (*Offsite*)

Ao menos uma cópia deve estar geograficamente distante do data center da empresa (em nuvem segura e imutável contra ransomware).

Protege contra desastres físicos
Quais são as modalidades técnicas de backup? Full vs Diferencial vs Incremental →
Módulo 5.1 • Tipologia de Rotinas

Os 3 Tipos de Backup: Full, Diferencial e Incremental

Comparativo Operacional
Tipo de Backup O que grava exatamente? Tempo para Executar Espaço Ocupado Tempo de Restauração
1. Completo (Full) Copia 100% dos dados, tabelas e estruturas do zero. Lento (horas) Muito Alto Ultra Rápido (Restaura só ele)
2. Diferencial Copia tudo o que mudou desde o último backup Full. Moderado Médio Rápido (Full + último Diferencial)
3. Incremental Copia apenas o que mudou desde o último backup de qualquer tipo. Ultra Rápido (minutos) Muito Baixo Mais lento (Full + todos os incrementais)
💡 A Estratégia Típica das Empresas: Backup Full no domingo à noite + Backup Incremental diário de segunda a sábado de madrugada!

Métricas Vitais de Recuperação: RPO & RTO

Disaster Recovery
RPO (Recovery Point Objective) Tolerância a Perdas

"Quantos dados a empresa tolera perder no tempo?"

É o intervalo máximo aceitável entre o último backup e o momento do desastre.

Exemplo: Se o backup roda a cada 1 hora, o RPO máximo é de 1 hora de dados perdidos. Em bancos, o RPO deve ser zero (replicação contínua síncrona).
RTO (Recovery Time Objective) Tempo de Parada

"Quanto tempo o sistema pode ficar fora do ar?"

É o tempo limite necessário para restaurar a infraestrutura e colocar o banco de dados operacional novamente para os clientes.

Exemplo: Se o e-commerce fatura R$ 100 mil/hora, um RTO de 4 horas significa R$ 400 mil de prejuízo imediato.
🚨 A Lei Suprema da TI: *"O estado de um backup é desconhecido até que você tente restaurá-lo com sucesso."* Faça simulações periódicas de recuperação de desastres!

Módulo 5.2 • Governança & Rastreabilidade

Rastreabilidade e Auditoria de Logs (*Audit Trail*)

Trilha Inviolável

Uma Trilha de Auditoria (Audit Trail) é o registro cronológico, imutável e detalhado de todas as operações realizadas dentro do banco de dados.

Os 5 Elementos Obrigatórios de um Log de Auditoria:
1. QUEM fez? (Usuário do banco e usuário da aplicação).
2. O QUE fez? (O comando executado: INSERT, UPDATE, DELETE, DROP).
3. QUANDO fez? (Data e hora exata em microssegundos com fuso horário UTC).
4. DE ONDE fez? (Endereço IP de origem e nome da máquina).
5. QUAL O IMPACTO? (Valor anterior vs novo valor gravado).
Conformidade Legal & Regulatória
LGPD (Art. 37 - Brasil) O controlador deve manter registro das operações de tratamento de dados pessoais para prestar contas à ANPD.
PCI-DSS (Requisito 10) Obrigatório rastrear e monitorar todo o acesso aos dados dos titulares de cartão de crédito.
SOX (Lei Sarbanes-Oxley) Auditoria de qualquer alteração manual em relatórios ou lançamentos contábeis corporativos.

Os 6 Pilares da Qualidade de Dados

Métricas de Confiabilidade
1

Acurácia (Precisão)

O dado reflete exatamente a realidade do mundo físico? (Ex: saldo bancário e estoque real nas prateleiras).

2

Completude

Todos os dados obrigatórios foram preenchidos ou existem lacunas vazias de e-mail e telefone?

3

Consistência

A informação concorda entre sistemas diferentes sem contradições? (Ex: endereço no CRM bate com o ERP?).

4

Validade

O dado obedece ao padrão e domínio esperado? (Ex: CPF com 11 dígitos válidos, e-mail com '@' e domínio real).

5

Unicidade

Cada entidade existe exatamente uma única vez, sem duplicidades de registros para o mesmo cliente.

6

Tempestividade (*Timeliness*)

O dado está disponível no momento certo para a tomada de decisão, sem atrasos de sincronização?

Big Data: Quando o Banco Convencional Não Dá Conta

Além dos Terabytes

O termo Big Data não se refere apenas a "muitos dados". Refere-se a conjuntos de dados tão volumosos, rápidos e variados que superam a capacidade dos softwares de bancos de dados relacionais tradicionais de capturar, armazenar e processar em tempo hábil.

A Quebra dos Limites Físicos Um único servidor comum não consegue processar 500 milhões de cliques por segundo ou 50 terabytes de logs diários de satélites e sensores de IoT.
Arquitetura de Processamento Paralelo Distribuído O Big Data resolve o desafio dividindo o problema entre centenas de computadores trabalhando em paralelo (frameworks como Apache Spark e Hadoop).
A Escala dos Dados no Mundo Hoje
~175 ZB Volume Global de Dados
80%+ Dados Não Estruturados
Fontes de Alimentação:

Telemetria de carros autônomos, câmeras de segurança, cliques de navegação em tempo real, transações de cartão de crédito e posts de redes sociais.

Data Warehouse vs Data Lake vs Lakehouse

Armazéns Analíticos
ESTRUTURADO

Data Warehouse (DW)

Armazém de dados 100% estruturados, limpos e modelados em esquemas estrela (*Star Schema*). Otimizado para consultas SQL analíticas de BI e dashboards executivos rápidos.

Snowflake, Google BigQuery, Redshift
DADOS BRUTOS

Data Lake

Um grande "lago" que armazena qualquer tipo de dado no formato bruto original (estruturado, semiestruturado e não estruturado) com custo baixíssimo de armazenamento.

Amazon S3, Azure Blob, Hadoop HDFS
A EVOLUÇÃO MODERNA

Data Lakehouse

A fusão do melhor dos dois mundos: traz a flexibilidade e baixo custo do Data Lake junto com as transações ACID e governança do Data Warehouse.

Databricks, Delta Lake, Apache Iceberg

Extração de Dados: ETL vs ELT

Pipelines de Dados
TRADICIONAL (ON-PREMISES)

ETL (Extract ➔ Transform ➔ Load)

Os dados são extraídos dos bancos operacionais, transformados e higienizados em um servidor intermediário antes de serem gravados no Data Warehouse.

Gargalo: O servidor de transformação intermediário pode virar um gargalo de processamento.
Ferramentas: Talend, SSIS, Pentaho.
MODERNO EM NUVEM

ELT (Extract ➔ Load ➔ Transform)

Os dados são extraídos e carregados brutos imediatamente no Data Warehouse em nuvem. A transformação ocorre depois, aproveitando o poder massivo de processamento distribuído da nuvem.

Vantagem: Muito mais rápido, flexível e sem perda do dado bruto original.
Ferramentas: dbt (data build tool), Fivetran, Airbyte.

Batch vs Streaming & O Formato Colunar Parquet

Alta Eficiência
Modos de Ingestão de Dados
1. Lote (Batch)

Os dados são acumulados e processados em blocos periódicos (ex: a cada 1 hora ou todas as noites à meia-noite).

2. Tempo Real (Streaming)

Cada evento é ingerido e processado no exato milissegundo em que acontece (ex: detecção de fraude de cartão no ato da compra).

Padrão da Indústria: Apache Kafka, Apache Flink
O Segredo do Big Data: Apache Parquet

Em vez de salvar linhas inteiras como no CSV, o Parquet armazena dados orientados por colunas com compressão extrema:

Arquivo em CSV (Texto Puro): 100 GB
Mesmo dado em Parquet (Snappy): 15 GB (85% menor!)
⚡ Consulta Seletiva: Se você pedir apenas a média de salários, o leitor de Parquet lê apenas aquela coluna do disco, ignorando as outras 50 colunas!

Gabarito Oficial e Guia Pedagógico

Questão 1: Regra 3-2-1 de Backup

Resposta Correta: Ter 3 cópias dos dados (1 produção + 2 backups), em 2 mídias distintas, com pelo menos 1 cópia fora do local físico (*offsite* / nuvem imutável).

Questão 2: Diferença entre RPO e RTO

Resposta Correta: O RPO mede o volume de dados que a empresa tolera perder no tempo (tolerância a perda); o RTO mede quanto tempo o sistema pode demorar para ser restabelecido (tempo de inatividade).

Questão 3: Prevenção contra SQL Injection

Resposta Correta: Utilizar Prepared Statements (Queries Parametrizadas), onde os dados digitados pelo usuário nunca são concatenados diretamente como código executável.

Questão 4: Regra 1-10-100 da Qualidade

Resposta Correta: O custo de prevenir um erro é muito baixo (R$ 1), corrigir o dado no banco custa 10 vezes mais (R$ 10) e arcar com o erro já no cliente custa 100 vezes mais (R$ 100).

Questão 5: Formato Parquet em Big Data

Resposta Correta: É um formato colunar com alta taxa de compressão que permite ler apenas as colunas solicitadas na consulta, economizando até 85% de I/O de disco.
