O que são Requisitos de Sistemas?

Módulo 10

📌 Conceito Essencial

Um requisito é uma condição ou capacidade que um software deve possuir para satisfazer a um objetivo do usuário, contrato, padrão ou regulamento. É o contrato invisível entre o cliente e o desenvolvedor.

🗣️

Necessidade Real

O problema que o usuário quer resolver no seu dia a dia.

📐

Especificação

A descrição detalhada de como o software atenderá essa demanda.

✅

Critério de Aceite

Como provar e testar que o software faz o que foi pedido.

⚠️ Atenção: Mais de 60% dos erros em projetos de software nascem na fase de levantamento de requisitos — corrigir um requisito errado durante o código custa até 10x mais; após a entrega, até 100x mais!

Do Problema ao Código

1. Desejo do Usuário
"Preciso achar produtos mais rápido na loja"
↓
2. Requisito de Sistema
"O sistema deve permitir busca por nome, categoria e faixa de preço com autocompletar em até 1s"
↓
3. Software Construído
Banco indexado + API de busca + Interface responsiva

O Grande Trio da Engenharia de Requisitos

Diferença Visual
RN — Regra de Negócio 🏢

A Regra da Organização

Define o que é permitido ou proibido segundo a lei, política ou diretriz da empresa (existe mesmo sem computador).

Exemplo Clássico:
"Cliente inadimplente não pode realizar compras a prazo."
👤 Origem: Diretoria, Jurídico, Financeiro.
RF — Requisito Funcional ⚙️

O QUE o Sistema Faz

Descreve uma ação, funcionalidade ou serviço que o sistema deve fornecer diretamente ao usuário.

Exemplo Clássico:
"O sistema deve consultar a situação cadastral do cliente antes de confirmar o pagamento parcelado."
💻 Origem: Usuários finais, Analistas de Sistemas.
RNF — Requisito Não Funcional 🛡️

COMO o Sistema Deve Ser

Define qualidade, restrições e desempenho com que a funcionalidade deve ser executada.

Exemplo Clássico:
"A validação de crédito deve ser concluída em até 2 segundos e trafegar via protocolo seguro HTTPS/TLS."
🛠️ Origem: Arquitetos, DevOps, Segurança, LGPD.
🏢

Regras de Negócio (RN) — As Normas da Empresa

Módulos 10.1 e 11

O que é uma Regra de Negócio?

É uma declaração que define ou restringe algum aspecto do negócio. Representa o conhecimento corporativo: diretrizes comerciais, políticas de segurança, leis governamentais e fórmulas de cálculo.

3 Exemplos Fundamentais do Mercado:

🚫
RN01 — Bloqueio de Inadimplência:
"Cliente inadimplente não pode realizar compras a prazo."
📦
RN02 — Trava de Estoque:
"Produtos sem estoque disponível não podem ser vendidos."
🔐
RN03 — Nível de Alçada / Permissão:
"Somente usuários com perfil 'Administrador' podem cancelar uma venda concluída."

🎯 Por que o sistema deve seguir as RNs?

  • 🔹 Evita prejuízos financeiros: impede vender fiado para quem já deve.
  • 🔹 Padroniza o atendimento: as regras valem igual para todos os caixas e lojas.
  • 🔹 Garante conformidade legal: respeita o Código de Defesa do Consumidor e impostos.
  • 🔹 Segurança operacional: operadores não cancelam vendas sem autorização do gerente.
💡 Dica Prática: Se a empresa fechar os computadores e voltar a usar papel e caneta, a Regra de Negócio continua valendo!
🧱

Estrutura de uma Regra de Negócio

Módulo 11.3

A Fórmula da Regra: Condição → Regra → Consequência

Para que uma regra possa ser programada sem erros, ela deve ser decomposta em 3 partes claras e inequívocas:

PASSO 1

1. Condição (SE)

O evento ou estado que dispara a verificação.

Ex: "SE o cliente possuir parcelas vencidas > 30 dias..."
PASSO 2

2. Regra / Critério

A restrição ou cálculo que deve ser aplicado.

Ex: "...o limite de crédito para crediário é BLOQUEADO..."
PASSO 3

3. Consequência / Ação

A resposta que o sistema deve executar.

Ex: "...o sistema recusa a venda a prazo e exige pagamento à vista."

Exemplo Aplicado: Desconto de Aniversário

SE mês do cliente = mês atual E compra >= R$ 100,00 ENTÃO aplicar 15% de desconto automaticamente no carrinho

🔍 Palavras-chave de Regras:

  • • "Deve conter..."
  • • "Não pode..."
  • • "Somente se..."
  • • "Obrigatório..."
  • • "O cálculo é feito por..."
  • • "Apenas o perfil X..."
⚙️

Requisitos Funcionais (RF) — O Que o Sistema Faz

Módulo 10.2

O que é um Requisito Funcional?

São os serviços, ações e comportamentos que o software deve executar em resposta às entradas do usuário. Se você perguntar: "O que esse botão faz?" ou "O que o sistema faz quando eu clico aqui?", a resposta é um Requisito Funcional!

As 5 Grandes Ações de um Requisito Funcional:

➕
Cadastrar

Inserir novos registros (Create)

🔍
Consultar

Pesquisar e listar dados (Read)

✏️
Alterar

Atualizar registros existentes (Update)

🗑️
Excluir

Remover ou inativar dados (Delete)

📊
Relatórios

Exportar PDFs, gráficos e métricas

💡
Formato Padrão de Escrita:
"O sistema deve [verbo de ação] [objeto da ação] [condições / parâmetros]."

Exemplos de RF no Mundo Real

RF01

Cadastrar Cliente

O sistema deve registrar nome, CPF, e-mail e telefone do cliente com validação de CPF.

RF02

Emitir Cupom Fiscal

O sistema deve gerar o arquivo XML e imprimir o DANFE após o fechamento do pedido.

RF03

Recuperar Senha

O sistema deve enviar um link de redefinição para o e-mail do usuário quando solicitado.

🛡️

Requisitos Não Funcionais (RNF) — Qualidade & Restrições

Módulo 10.3

O que é um Requisito Não Funcional?

Não diz respeito a o que o sistema faz, mas sim a como ele se comporta enquanto executa suas funções. Tratam de desempenho, segurança, robustez, conformidade com a LGPD e experiência do usuário.

🚗 A Clássica Analogia Automotiva:

Requisito Funcional (Ação):

O carro deve acelerar, frear, ligar o farol e tocar música.

Requisito Não Funcional (Qualidade):

O carro deve acelerar de 0 a 100 km/h em 7s, ter airbag lateral e consumir 15 km/l.

💬 Regra de Ouro: Um RNF sem métrica numérica é apenas um "desejo". Em vez de dizer "o sistema deve ser rápido", especifique: "o tempo de resposta não deve passar de 2 segundos".

⚠️ O que acontece quando o RNF é ignorado?

  • ❌ O sistema calcula a venda perfeitamente, mas trava na Black Friday por falta de escalabilidade.
  • ❌ O cadastro funciona, mas vaza senhas em texto puro por falta de criptografia.
  • ❌ O botão existe, mas o usuário não consegue usar no celular porque não é responsivo.
🏛️

Os 5 Pilares dos Requisitos Não Funcionais

Módulo 10.3
⚡

1. Desempenho

Velocidade de processamento, tempo de resposta e consumo de memória.

Meta: "Consultas de saldo respondidas em < 500ms sob 5.000 usuários simultâneos."
🔒

2. Segurança

Proteção contra ataques, controle de acesso e conformidade com a LGPD.

Meta: "Senhas com hash bcrypt + sal; dados trafegados exclusivamente com TLS 1.3."
🟢

3. Disponibilidade

Tempo em que o sistema permanece no ar sem interrupção de serviço.

Meta: "Disponibilidade de 99,9% (máximo de 8,7 horas fora do ar por ano)."
📱

4. Usabilidade

Facilidade de aprendizado, ergonomia e acessibilidade a deficientes visuais.

Meta: "Operador novato deve emitir um pedido em até 3 minutos sem ajuda externa."
🛡️

5. Integridade

Garantia de que os dados não serão corrompidos ou perdidos em falhas.

Meta: "Transações bancárias com propriedades ACID e backup a cada 1 hora."
📊

Quadro Comparativo: RN vs. RF vs. RNF

Síntese Prática
Critério Regra de Negócio (RN) Requisito Funcional (RF) Requisito Não Funcional (RNF)
Pergunta Central "Qual é a norma da empresa?" "O que o sistema deve fazer?" "Com que qualidade deve operar?"
Depende de TI? Não. Existe mesmo se a loja for 100% manual no papel. Sim. É uma funcionalidade construída no software. Sim. É uma característica da arquitetura do software.
Exemplo no Varejo "Produtos sem estoque não podem ser faturados." "O sistema deve verificar o saldo em estoque antes de finalizar a venda." "A verificação do estoque deve ser em tempo real e durar menos de 300ms."
Exemplo de Acesso "Somente gerentes podem autorizar descontos > 15%." "O sistema deve solicitar login e senha do gerente para aprovar desconto especial." "A autenticação deve bloquear após 3 tentativas inválidas consecutivas."
Quem Especifica? Diretores, gerentes, contadores, advogados. Analistas de requisitos e usuários finais. Arquitetos de software, segurança e infraestrutura.
🎯 Resumo memorável: A RN diz o que a empresa exige; o RF cria a ferramenta para cumprir; o RNF garante que funcione com excelência.

Técnicas de Levantamento e Análise de Requisitos

Módulo 10.4

Como descobrir o que o cliente realmente precisa?

Raramente o cliente sabe descrever os requisitos de forma técnica. O analista de sistemas utiliza técnicas investigativas para extrair as necessidades reais:

🎙️ Entrevistas

Conversas diretas (abertas ou estruturadas) com usuários e gestores-chave.

📝 Questionários

Formulários para coletar opiniões de muitos usuários dispersos geograficamente.

👀 Observação (Shadowing)

Acompanhar o operador trabalhando na prática para ver o que ele esquece de contar.

👥 Workshops (JAD)

Reuniões com todos os setores juntos para alinhar conflitos de interesses.

📑 Análise Documental

Examinar planilhas atuais, relatórios fiscais, manuais e sistemas legados.

🎨 Prototipação

Criar telas simuladas (wireframes no Figma) para o cliente testar e validar.

💡 Dica de Ouro

"O usuário não sabe o que quer até ver o protótipo na frente dele."

Use protótipos visuais antes de escrever código no backend!

⚠️ Atenção: Sempre combine ao menos duas técnicas (ex: entrevista + observação de documentos) para não ter visão enviesada.

Validação de Requisitos — Evitando Desastres

Qualidade do Projeto

O que é Validar um Requisito?

É a confirmação formal com o cliente de que os requisitos documentados representam exatamente a solução esperada, sem ambiguidades ou conflitos.

Critérios para um Requisito Válido:

1. Claro & Inequívoco: Não dá margem para duas interpretações diferentes.
2. Completo: Descreve todas as entradas necessárias e o que acontece quando dá erro.
3. Consistente: Não contradiz nenhum outro requisito nem nenhuma regra de negócio.
4. Testável / Verificável: A equipe de testes consegue criar um teste objetivo para provar que funciona.
5. Viável: É possível ser desenvolvido dentro do prazo, orçamento e tecnologia disponíveis.

Custo Relativo da Correção de Erros

Descobrir um erro em produção custa até 100 vezes mais do que corrigi-lo na fase de requisitos!

Estudo de Caso Prático: O E-commerce Completo

Aplicação Real

Cenário: Loja Virtual "TechExpress"

Veja como o levantamento de requisitos de uma mesma tela (o Carrinho de Compras) conecta as três esferas:

1. As Regras de Negócio

RN01: Produtos sem estoque físico disponível não podem ser adicionados ao carrinho.

RN02: Compras acima de R$ 250,00 possuem frete grátis para a região Sudeste.

Normas Comerciais da TechExpress
2. Os Requisitos Funcionais

RF01: O sistema deve calcular o frete com base no CEP digitado e aplicar desconto automático se atingir a meta.

RF02: O sistema deve permitir alterar a quantidade de itens ou excluir produtos diretamente na tela do carrinho.

O que o sistema executa
3. Os Requisitos Não Funcionais

RNF01: O recálculo dos valores após alteração de quantidade deve ocorrer em menos de 500ms.

RNF02: A página do carrinho deve ser 100% responsiva e acessível para leitores de tela (WCAG 2.1).

Qualidade da experiência
💡 Repare na harmonia: nenhum dos três substitui o outro. Um software só tem sucesso quando atende aos três plenamente!
