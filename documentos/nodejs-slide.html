Módulo 2 • Runtime

O que é Node.js e por que utilizá-lo?

Node.js não é uma linguagem ou framework: é um ambiente de execução (runtime) que roda JavaScript fora do navegador.

⚡ Motor V8 do Google Chrome

Executa JavaScript compilado diretamente para código de máquina ultra-rápido.

🔄 Assíncrono & Não Bloqueante (Event Loop)

Capacidade de lidar com milhares de requisições simultâneas com baixo consumo de memória.

🌐 Mesma Linguagem Ponta a Ponta

Você utiliza JavaScript tanto no Frontend quanto no Backend, compartilhando conhecimentos e tipos.

index.js & Terminal
// 1. Código JavaScript no arquivo index.js
console.log("Olá, Servidor Node.js!");
# 2. Executando via linha de comando:
$ node index.js
Olá, Servidor Node.js!
🎯 No navegador: temos window e document.
🎯 No Node.js: temos process, fs (arquivos) e http.

Módulo 4 • Hello Server

Criando nosso Primeiro Servidor com Express

Express é o microframework mais popular do Node.js: simplifica roteamento, requisições e respostas HTTP.

server.js
// 1. Importa o Express
const express = require("express");

// 2. Instancia a aplicação
const app = express();
app.use(express.json()); // suporte a JSON

// 3. Rota de teste
app.get("/", (req, res) => {
return res.json({ message: "API no ar! 🚀" });
});

// 4. Abre a porta do servidor
app.listen(3000, () => {
console.log("Servidor rodando em http://localhost:3000");
});
require("express")

Carrega o módulo Express instalado através do NPM via sistema CommonJS.

app.get("/", (req, res) => ...)

Registra um ouvinte para requisições do tipo GET na raiz. req traz dados do cliente e res envia a resposta.

app.listen(3000)

Coloca o servidor em modo de escuta ativa na porta 3000 do computador local (localhost).

Resposta no navegador em http://localhost:3000:
{ "message": "API no ar! 🚀" }
Módulo 5 • Comunicação Web

Protocolo HTTP: Métodos e Status Codes

O protocolo HTTP define a semântica da web: ações intencionais através de verbos e respostas por códigos.

⚡ Principais Verbos HTTP

GET Buscar / Ler dados /users
POST Criar novo registro /users
PUT Atualizar todo o registro /users/:id
PATCH Atualizar campo parcial /users/:id
DELETE Excluir um registro /users/:id

🚥 Códigos de Status Mais Usados

200 OK Sucesso genérico na operação
201 Created Recurso criado com êxito
204 No Content Sucesso sem corpo de retorno (ex: DELETE)
400 Bad Request Dados enviados inválidos ou ausentes
404 Not Found Recurso ou rota não encontrada
500 Server Error Falha inesperada no código do servidor
Módulo 6 • Padrão Arquitetural

O que define uma API REST?

REST (Representational State Transfer) é um padrão que padroniza rotas em torno de recursos (substantivos) e não de ações.

Modelando Endpoints:

❌ NÃO RECOMENDADO (Ação na URL)
GET /getUsers
POST /criarUsuario
POST /deleteUser?id=10
✔ PADRÃO REST (Substantivo no plural)
GET /users ➔ Lista todos
POST /users ➔ Cria usuário
DELETE /users/10 ➔ Deleta o ID 10

📦 Recurso (Resource)

A entidade manipulada pelo sistema (ex: Usuário, Produto, Pedido). Sempre nomeada no plural.

📄 Formato JSON Universal

O intercâmbio de dados ocorre via JSON (JavaScript Object Notation), legível por qualquer tecnologia.

⚡ Stateless (Sem Estado)

Cada requisição carrega todas as informações necessárias para ser processada, sem depender de sessões salvas no servidor.

Módulo 7 • Arquitetura

Estrutura Profissional de Arquivos

Por que nunca devemos colocar todo o código em um único arquivo server.js?

📁 api-node/
├── 📁 src/
├── 📁 routes/ // user.routes.js
├── 📁 controllers/ // user.controller.js
├── 📁 services/ // user.service.js
├── 📁 models/ // user.model.js
├── 📁 middlewares/ // auth.middleware.js
└── 📄 app.js // Configura o Express
├── 📄 server.js // Inicializa a porta
├── 📄 package.json
└── 📄 .gitignore

🎯 Separação de Responsabilidades (SoC)

Cada arquivo tem uma única razão para mudar. Quem cuida de rota não cuida de regra matemática.

🧪 Facilidade de Testes Unitários

Podemos testar o user.service.js sem precisar levantar o servidor HTTP ou fazer requisições reais.

👥 Trabalho em Equipe Sem Conflitos

Vários desenvolvedores podem criar módulos diferentes ao mesmo tempo sem colidir no Git.

Módulo 8 • Camada 1

Routes: O Recepcionista da API

A rota identifica qual método e URL foram chamados e encaminha para o Controller competente.

src/routes/user.routes.js
const express = require("express");
const router = express.Router();
const userController = require("../controllers/user.controller");

// Mapeamento dos Endpoints
router.get("/users", userController.index);
router.get("/users/:id", userController.show);
router.post("/users", userController.store);
router.put("/users/:id", userController.update);
router.delete("/users/:id", userController.destroy);

module.exports = router;

Regra de Ouro das Rotas:

Uma rota deve ser "magra". Ela não deve conter cálculos, consultas a banco de dados ou ifs complexos. Sua única missão é ligar um caminho a um método do Controller.

express.Router()

Permite modularizar rotas em arquivos separados e depois acoplá-las no app.js principal com app.use(userRoutes).

:id (Parâmetro de Rota)

Os dois pontos indicam que aquele segmento é dinâmico (ex: /users/1, /users/42).

Módulo 9 • Camada 2

Controllers: O Atendente da Requisição

O Controller recebe os dados do HTTP, chama a regra de negócio no Service e retorna a resposta com o status code correto.

src/controllers/user.controller.js
const userService = require("../services/user.service");

async function index(req, res) {
const users = await userService.getAll();
return res.json(users);
}

async function store(req, res) {
const { name, email } = req.body;
const newUser = await userService.create({ name, email });
return res.status(201).json(newUser);
}

module.exports = { index, store };

As 4 Tarefas do Controller:

  • Extrair dados da requisição (params, query, body)
  • Fazer validações básicas de formato de entrada
  • Delegar a execução para o Service
  • Enviar a resposta HTTP (res.status().json())
⚠️ O que NÃO colocar no Controller:

Nunca escreva consultas SQL diretas ou lógicas de cálculo no Controller. Se amanhã você trocar o Express por outro framework, o Service continuará funcionando intacto!

Módulo 10 • Camada 3

Services: O Especialista em Negócio

O Service é o coração da aplicação: onde ficam todas as regras, validações lógicas e cálculos da sua empresa.

src/services/user.service.js
const userModel = require("../models/user.model");

async function create({ name, email }) {
// 1. Regra de Negócio: email deve ser único
const exists = await userModel.findByEmail(email);
if (exists) {
throw new Error("E-mail já cadastrado!");
}

// 2. Gravação através do Model
return await userModel.create({ name, email });
}

module.exports = { create };

Exemplos de Regras de Negócio:

  • Verificar se o CPF/CNPJ é válido
  • Checar se a idade mínima para cadastro foi atingida
  • Disparar e-mail de boas-vindas após cadastro
  • Aplicar desconto em pedidos promocionais
Totalmente agnóstico ao Express!

Note que no user.service.js não existe req ou res! O Service trabalha apenas com parâmetros puros de JavaScript.

Módulo 11 • Camada 4

Models: Acesso e Manipulação dos Dados

O Model conversa diretamente com a fonte de dados (nesta aula, um array em memória simulando um banco).

src/models/user.model.js (Em Memória)
// Simula nossa tabela de usuários
const users = [
{ id: 1, name: "Phelipe", email: "phelipe@email.com" }
];

function findAll() { return users; }

function findById(id) {
return users.find(u => u.id === Number(id));
}

function create({ name, email }) {
const newUser = { id: Date.now(), name, email };
users.push(newUser);
return newUser;
}

module.exports = { findAll, findById, create };

Futuro com Banco de Dados Real:

Quando seu projeto crescer e for conectar em um PostgreSQL ou MongoDB (usando Prisma, TypeORM ou Sequelize), apenas este arquivo Model será reescrito! O Controller e as Rotas continuarão iguaizinhos.

Bancos Suportados no Ecossistema:
PostgreSQL MySQL MongoDB Prisma ORM

O Fluxo Completo de uma Requisição

Veja como as quatro camadas trabalham em perfeita harmonia desde o clique até a resposta.

💻 1. CLIENTE GET /users/10 Dispara Request
🛣️ 2. ROUTE /users/:id Identifica caminho
🎮 3. CONTROLLER req.params.id Coordena chamada
⚙️ 4. SERVICE validaRegras() Executa a lógica
📦 5. MODEL findById(10) Retorna o registro
🔄 Retorno em cascata reversa: Model ➔ Service ➔ Controller ➔ res.json({ user }) ➔ Cliente (HTTP 200)
Módulo 13 • Objetos do Express

Os 3 Formatos de Envio: Params, Query e Body

Como extrair dados enviados pelo cliente no objeto req do Express.

1. Route Params
Usado para identificar um recurso único na URL.
GET /users/10
Como ler no código:
req.params.id // "10"
2. Query Params
Usado para filtros, paginação e ordenação opcionais.
GET /users?role=admin&page=2
Como ler no código:
req.query.role // "admin"
3. Request Body
Usado para payloads maiores em POST e PUT (JSON).
{ "name": "Ana", "email": "ana@..." }
Como ler no código:
req.body.name // "Ana"
⚠️ Atenção: Para que req.body funcione no Express, lembre-se sempre de habilitar app.use(express.json()) no seu arquivo de entrada!
Módulo 14 • Interceptação

Middlewares: A Portaria do Servidor

Funções intermediárias executadas no meio do caminho entre a chegada da requisição e o Controller final.

Exemplo de Middleware de Log
function loggerMiddleware(req, res, next) {
const time = new Date().toISOString();
console.log(`[${time}] ${req.method} em ${req.url}`);

// Libera para a próxima etapa:
next();
}

// Aplicando globalmente em todas as rotas:
app.use(loggerMiddleware);

O Poder do next()

Se você não chamar next() e não retornar uma resposta com res.json(), a requisição ficará "travada" aguardando para sempre até estourar timeout!

Principais Usos de Middlewares:

🔐 Autenticação: Checar se o token JWT é válido
📝 Logging & Métricas: Monitorar tempo de resposta
🛡️ Segurança (CORS / Helmet): Bloquear origens suspeitas
💥 Tratamento de Erros: Capturar exceções globais
Módulo 15 • Operações Essenciais

CRUD: As 4 Operações Básicas

Quase todo sistema de software é, no seu núcleo, uma composição de Create, Read, Update e Delete.

Operação Verbo HTTP Endpoint Ação / Descrição Status Esperado
Create POST /users Cadastra um novo usuário no banco 201 Created
Read (Todos) GET /users Lista todos os usuários cadastrados 200 OK
Read (Individual) GET /users/:id Retorna os detalhes de um único usuário por ID 200 OK
Update PUT /users/:id Atualiza os dados de um usuário existente 200 OK
Delete DELETE /users/:id Remove o usuário da base de dados 204 No Content
Módulo 16 • Implementação

Implementando o CRUD em Memória

Veja como as operações de atualização e exclusão acontecem sobre a estrutura de dados.

PUT /users/:id (Atualizar)
function update(id, { name, email }) {
  const user = findById(id);
  if (!user) return null;

  if (name) user.name = name;
  if (email) user.email = email;

  return user;
}
DELETE /users/:id (Excluir)
function destroy(id) {
  const index = users.findIndex(
    u => u.id === Number(id)
  );
  
  if (index === -1) return false;

  users.splice(index, 1);
  return true;
}
💡 Nota didática: Usar um array em memória é perfeito para aprender os conceitos de rotas e status sem a distração de configurar credenciais de bancos de dados no primeiro dia!
Módulo 17 • Integridade

Validação: Nunca Confie no Cliente

Quem consome a API pode enviar dados incompletos, tipos errados ou informações maliciosas.

Validação manual no Controller
async function store(req, res) {
const { name, email } = req.body;

// Validação de presença obrigatória:
if (!name || !email) {
return res.status(400).json({
error: "Nome e e-mail são obrigatórios!"
});
}

const user = await userService.create({ name, email });
return res.status(201).json(user);
}

Regras Essenciais de Validação:

  • Campos obrigatórios preenchidos
  • Formato correto de e-mail (conter @ e domínio)
  • Tamanho mínimo e máximo de caracteres
  • Tipagem adequada (número x texto)
Bibliotecas Avançadas (Próximo Nível):

Em projetos corporativos, usamos bibliotecas de validação com schemas como Zod ou Yup para validar objetos complexos automaticamente.

Módulo 18 • Resiliência

Tratamento de Erros Previsível

Uma boa API nunca deixa a requisição sem resposta ou expõe rastros técnicos (stack trace) para o usuário final.

1. try / catch no Controller
try {
const user = await userService.getById(id);
return res.json(user);
} catch (error) {
return res.status(404).json({
error: error.message
});
}
2. Middleware Global de Erros
// Tem 4 parâmetros (o primeiro é 'err')
app.use((err, req, res, next) => {
console.error(err.stack);

return res.status(500).json({
error: "Ocorreu um erro interno no servidor"
});
});
🎯 Regra de Ouro: Sempre retorne respostas com formato consistente em JSON: { "error": "motivo claro" }.

👨‍🏫 MATERIAL EXCLUSIVO DO PROFESSOR • GABARITO

Respostas Explicativas das Questões

Gabarito Oficial
1. O que é Node.js?

É um ambiente de execução (runtime) baseado no motor V8 do Chrome que permite executar JavaScript no lado do servidor com I/O assíncrono e não-bloqueante, unificando a linguagem no ecossistema web completo.

2. Controller vs. Service

O Controller lida com o protocolo HTTP (extrair req.body, params e enviar res.status().json()). O Service contém a lógica de negócio pura (regras, cálculos e validações), sendo 100% independente do framework web.

3. Papel do Model

O Model encapsula o acesso e a manipulação dos dados. Isso isola a aplicação do banco de dados específico, permitindo trocar o banco ou ORM no futuro sem quebrar o restante da API.

4. Esquecer de invocar next()

A requisição fica suspensa em espera infinita (hanging request), resultando em travamento do cliente ou erro de Timeout (504 Gateway Timeout), pois o fluxo do Express não sabe para onde continuar.

5. Vantagem da Arquitetura em Camadas

Separação de responsabilidades (SoC), facilidade de manutenção, facilidade para escrever testes unitários e capacidade da aplicação escalar organizadamente com grandes equipes.
