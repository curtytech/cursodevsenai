0. Antes de tudo: o que o VS Code é — e o que ele não é

O VS Code é um editor de código extensível. Ele organiza arquivos, entende linguagens, integra terminal, depuração, controle de versão e extensões. Mas ele não substitui o sistema operacional, a linguagem, o compilador ou o navegador.

Mapa mental: seus arquivos existem no computador → o VS Code abre uma pasta → o Explorer mostra os arquivos → o Editor altera → o Terminal executa comandos → Problems/Output/Debug mostram diagnósticos → Git registra mudanças.

Uma confusão clássica: “meu projeto está dentro do VS Code”. Na prática, não. O projeto está em uma pasta real do disco. O VS Code apenas mostra e trabalha com essa pasta. Se você fechar o editor, os arquivos continuam lá.

Outra confusão: “VS Code roda JavaScript”. Quem executa JavaScript pode ser o navegador ou o Node.js. O VS Code oferece o ambiente para escrever e acionar essas ferramentas.

Coisa que quase ninguém ensina: muitos erros atribuídos ao VS Code pertencem a outra camada: PATH do sistema, shell, Git, Node, extensão, navegador ou linguagem. Aprender a identificar qual camada está falhando é uma habilidade profissional.

2. Explorer: arquivos, pastas e a raiz do projeto

O Explorer é seu mapa de arquivos. Para iniciantes, entender “raiz”, caminhos e pasta aberta evita muitos problemas.

meu-projeto/
├── index.html
├── css/
│   └── style.css
├── js/
│   └── app.js
└── imagens/
    └── logo.png

A pasta meu-projeto é a raiz. Um caminho como js/app.js é relativo a essa raiz.

Abra a pasta, não apenas um arquivo. Quando você usa File → Open Folder, o VS Code passa a ter contexto do projeto. Isso influencia terminal, Git, configurações e extensões.

Ao criar, mover ou renomear arquivos pelo Explorer, você está alterando arquivos reais no sistema. Não é uma “cópia virtual”.

Detalhe pouco ensinado: o VS Code pode lembrar estado por workspace: arquivos abertos, layout e outras informações. Por isso dois projetos podem abrir com aparências diferentes.

3. O que realmente é um Workspace

Termo técnico — contexto: quando dizemos que o VS Code tem “contexto do projeto”, significa que ele sabe qual pasta/workspace está aberto e pode usar isso para localizar arquivos, configurações, Git e ferramentas. Não significa que ele automaticamente entende toda a lógica da aplicação.

Workspace é o contexto de trabalho. Muitas vezes ele corresponde a uma pasta, mas também pode representar múltiplas pastas e configurações específicas.

Arquivo isolado: útil para uma edição rápida. Pasta/workspace: ideal para um projeto real.

Configurações de workspace podem ser guardadas na pasta .vscode, dependendo do recurso. Isso permite que um projeto tenha comportamento específico sem mudar seus outros projetos.

Não apague a pasta .vscode sem entender. Ela pode conter configurações, tasks ou launch configurations úteis ao projeto.
Multi-root workspace: o VS Code pode trabalhar com mais de uma pasta no mesmo workspace. É útil em projetos maiores, mas você não precisa disso no início. O importante é saber que “workspace” é um conceito maior que “um arquivo”.

4. Editor: edição, IntelliSense e recursos essenciais

Termo técnico — símbolo: variável, função, classe ou método são exemplos de elementos nomeados que ferramentas podem tratar como símbolos. Language Server é um serviço que várias linguagens usam para analisar código em segundo plano e fornecer sugestões, definições, referências e diagnósticos.

O editor não é apenas um bloco de notas. Ele entende linguagens e pode fornecer sugestões, navegação, formatação e refatoração.

Coisa pouco ensinada: as cores do código não controlam o programa. Se o código muda de cor, isso pode ser apenas tema ou modo de linguagem. O funcionamento real depende da linguagem e execução.

5. Edição eficiente: recursos que economizam horas

Editar código não é apenas digitar. Um bom editor permite selecionar, mover, repetir, transformar e navegar pelo texto com muito menos esforço. Nesta aula, o objetivo é entender o que o VS Code faz no documento, e não apenas decorar atalhos.

Ideia principal: produtividade não é digitar rápido. É reduzir ações repetitivas, cometer menos erros e manter sua atenção no problema.

5.1 Cursor, seleção, linha e coluna

Fundamento

O cursor indica onde o próximo caractere será inserido. Uma seleção é um trecho marcado para receber uma ação. Uma linha é delimitada por uma quebra de linha. A coluna indica a posição horizontal do cursor.

<h1>Olá, mundo!</h1>
               ↑ cursor

A Status Bar mostra algo como Ln 15, Col 8: linha 15, coluna 8. Esse detalhe é muito útil quando uma mensagem de erro aponta uma posição específica.

5.2 Mover linhas

Alt + ↑ / ↓

No Windows/Linux, Alt + ↑ ou Alt + ↓ move a linha atual. É mais seguro e rápido que selecionar, recortar, procurar o destino e colar.

<h1>Título</h1>
<p>Primeiro</p>
<p>Segundo</p>
Pratique: mova Segundo para cima e depois devolva ao lugar.

5.3 Duplicar linha ou seleção

Repetição controlada

Quando duas estruturas serão parecidas, duplicar evita redigitar tudo. Procure Copy Line Down na Command Palette e observe o atalho configurado no seu sistema.

<button>Salvar</button>
<button>Cancelar</button>
Cuidado: a ferramenta é útil, mas copiar grandes blocos de código repetidamente pode ser sinal de que o programa deveria ser reorganizado.

5.4 Múltiplos cursores

Editar vários pontos

O VS Code permite manter várias posições de edição no mesmo documento. No Windows/Linux, uma forma comum é segurar Alt e clicar em diferentes posições.

<li>Produto</li>
<li>Produto</li>
<li>Produto</li>

Com três cursores antes de Produto, digitar Novo altera as três linhas simultaneamente.

O que acontece tecnicamente? Você continua editando um único arquivo. O editor mantém várias posições/seleções e aplica a mesma operação a elas.
Esc normalmente retorna a um único cursor. Confira as posições antes de digitar.

5.5 Selecionar próxima ocorrência

Ctrl + D

Selecione uma palavra e use Ctrl + D. O VS Code adiciona a próxima ocorrência igual à seleção. É ótimo quando você quer alterar algumas ocorrências, não todas.

Não confunda com Replace All: Ctrl+D permite escolher progressivamente. Replace All altera todas as correspondências dentro do escopo.

5.6 Find, Replace e Replace All

Ctrl + F / Ctrl + H

Find procura texto. Replace procura e substitui. Opções como Match Case diferenciam maiúsculas/minúsculas; Whole Word exige palavra inteira; e Regex usa padrões especiais.

Antes de Replace All: veja quantas ocorrências foram encontradas e confirme se a busca é específica o suficiente.

5.7 Rename Symbol não é Replace

F2 quando suportado

Replace trabalha com texto. Rename Symbol pode trabalhar com o significado do código quando o suporte da linguagem entende aquele símbolo.

const nome = "Magno";
console.log(nome);

Uma variável, função, classe ou método pode ser um símbolo. Renomeá-lo com uma ferramenta de linguagem é uma forma simples de refatoração: reorganizar o código preservando sua intenção/comportamento.

5.8 Indentação: Spaces, Tabs e caracteres invisíveis

Estrutura visual
if (usuarioLogado) {
    console.log("Bem-vindo");
}

A Status Bar pode mostrar Spaces: 4. Pressionar a tecla Tab não significa obrigatoriamente salvar um caractere TAB: o editor pode inserir espaços conforme a configuração.

Spaces × Tab: são diferentes. Espaços, tabs e quebras de linha são caracteres/estruturas que normalmente não enxergamos. Procure Render Whitespace para visualizá-los.

5.9 Word Wrap

Alt + Z

Word Wrap faz uma linha longa continuar visualmente embaixo quando falta espaço horizontal.

Ele não adiciona Enter. O arquivo continua contendo a mesma linha. É uma mudança de visualização, não de conteúdo.

5.10 Comentários

Ctrl + /

Comentários são trechos que a linguagem normalmente ignora durante a execução e podem documentar decisões ou auxiliar testes temporários.

// comentário JavaScript
/* comentário
   em bloco */

Toggle Line Comment usa a sintaxe adequada ao modo de linguagem atual.

Não deixe grandes quantidades de código antigo comentado “por garantia”. Git existe para preservar histórico.

5.11 Format Document e Format On Save

Formatação ≠ correção lógica

Formatar reorganiza aspectos como indentação, espaços e quebras conforme regras de um formatador. Isso não significa corrigir a lógica do programa.

Se houver mais de um formatador, pode ser necessário definir um Default Formatter. Format On Save solicita formatação quando o arquivo é salvo.

Se Format On Save não fizer nada, pode não existir um formatador aplicável ou um padrão selecionado. A configuração sozinha não “inventa” um formatador.

5.12 Undo, Redo e Git são coisas diferentes

Histórico de edição

Ctrl+Z desfaz operações recentes. Redo reaplica uma operação desfeita.

Undo não é backup e não é Git. Undo pertence à edição atual. Git cria pontos de versionamento do projeto. São camadas diferentes.

5.13 Preview Tab: por que uma aba parece desaparecer

Comportamento do editor

Um único clique em um arquivo pode abri-lo em modo Preview. Ao clicar em outro arquivo, a aba de preview pode ser reutilizada.

O arquivo não foi apagado. É apenas uma estratégia do VS Code para não criar dezenas de abas durante a navegação. Esse comportamento é relacionado a configurações como workbench.editor.enablePreview.

5.14 Fechamento automático de pares

() [] {} ""

Ao digitar (, [, { ou aspas, o editor pode inserir automaticamente o fechamento. Ele também pode envolver uma seleção com determinados pares.

“O editor digitou sozinho?” Algumas automações vêm do editor, outras do suporte da linguagem e outras de extensões. Saber que existem essas camadas ajuda a investigar comportamentos inesperados.

5.15 Snippets e Emmet

Automação consciente

Snippet é um modelo de código expansível. Emmet permite abreviações muito úteis em HTML/CSS.

ul>li*3

Em HTML, essa abreviação pode gerar uma lista com três itens quando o Emmet está disponível.

Para aprender: use Emmet somente depois de entender o HTML gerado. Ele deve economizar digitação, não esconder o conhecimento.

  2. Duplique uma linha.
  3. Mova uma linha para cima e para baixo.
  4. Use múltiplos cursores para editar três textos.
  5. Use Ctrl+D.

Objetivo: explicar não apenas qual tecla apertou, mas qual transformação o editor realizou no documento.

9. Terminal integrado — do zero e sem mistério

O terminal é uma das partes que mais assustam iniciantes porque mistura VS Code, sistema operacional e ferramentas externas.

Terminal

A interface onde você digita e vê saída.

Shell

O programa que interpreta os comandos: PowerShell, Bash, Zsh, entre outros.

Comando

A instrução enviada ao shell: cd, git, node, etc.

Abra em View → Terminal ou com Ctrl+`.

Diretório atual

PS C:\Users\Aluno\projetos\lista-tarefas>

Esse texto indica que o terminal está dentro da pasta lista-tarefas. Muitos erros de “arquivo não encontrado” acontecem porque o terminal está em outra pasta.

ComandoIdeia
pwdMostra o diretório atual em shells compatíveis.
lsLista itens.
cd pastaEntra em uma pasta.
cd ..Volta um nível.
Shell Integration: o VS Code pode entender melhor comandos e diretórios do shell, adicionando navegação por comandos recentes, detecção de diretório e outras integrações. O terminal integrado é mais do que “uma caixa preta”.
Nunca execute um comando desconhecido só porque foi copiado da internet. Terminal pode criar, apagar e executar arquivos.

10. PATH: por que “git/node/code não é reconhecido”

Executável e variável de ambiente: um executável é um programa que o sistema pode iniciar. PATH é uma variável de ambiente — um valor disponibilizado aos processos — que contém locais onde o shell pode procurar programas chamados pelo nome.

Quando você digita o nome de um programa no terminal, o sistema precisa encontrá-lo.

PATH é, de forma simplificada, uma lista de diretórios onde o sistema procura executáveis.

Se você instalou Node.js agora e um terminal antigo não reconhece node, fechar e reabrir o terminal — e às vezes o VS Code — pode fazer o novo ambiente ser carregado.

Não edite PATH aleatoriamente. É uma configuração compartilhada por diversas ferramentas.
Diagnóstico: se um comando funciona no PowerShell externo mas não no terminal do VS Code, compare shell, ambiente e quando cada processo foi aberto.

11. Problems, Output, Terminal e Debug Console

Log × diagnóstico: um log é um registro de eventos produzido por uma ferramenta; nem todo log é erro. Um diagnóstico é uma mensagem de análise do código, como erro, aviso ou sugestão, e muitos aparecem em Problems.

Essas áreas são confundidas o tempo todo.

ÁreaPrincipal função
ProblemsErros e avisos identificados por ferramentas de análise.
OutputLogs do VS Code e de extensões.
TerminalExecutar comandos no shell.
Debug ConsoleSaída e avaliação durante uma sessão de depuração.
Método profissional: ao ver um erro, pergunte “quem gerou esta mensagem?”. Navegador? Git? Terminal? Extensão? Linter? Debugger? A origem muda completamente a solução.

12. Settings: User × Workspace

Quase todo comportamento do VS Code pode ser configurado. O ponto difícil é entender o escopo.

User Settings

Suas preferências gerais, aplicadas a vários projetos.

Workspace Settings

Preferências específicas do projeto atual e que podem sobrescrever as de usuário.

Language-specific

Algumas configurações podem valer apenas para uma linguagem.

Abra com Ctrl+,. A interface gráfica altera as mesmas configurações que também podem aparecer em settings.json.

{
  "editor.fontSize": 16,
  "editor.wordWrap": "on",
  "files.autoSave": "afterDelay",
  "editor.formatOnSave": true
}
Format On Save não cria um formatador. Ele pede formatação ao salvar, mas precisa existir um formatador aplicável.
Filtro útil: a busca de Settings suporta filtros como @modified, útil para ver o que você mudou em relação ao padrão.

13. Auto Save, arquivos “sujos” e salvamento real

Modificar o conteúdo no editor e gravar no disco não são necessariamente a mesma coisa.

Quando um arquivo tem alterações ainda não salvas, o VS Code apresenta um indicador na aba. Com Auto Save desativado, Ctrl+S grava manualmente.

Auto Save pode ser configurado para diferentes comportamentos. Para estudar, salvar manualmente também tem valor porque ajuda a perceber quando o arquivo realmente foi gravado.

Git vê arquivos gravados no disco. Se você está comparando mudanças e algo não aparece como esperado, verifique se o arquivo foi salvo.

14. UTF-8, CRLF/LF e Language Mode

Byte e caracteres invisíveis: arquivos são armazenados como bytes. O encoding define como bytes representam caracteres. Espaços, tabs e quebras de linha também fazem parte do arquivo, embora normalmente não apareçam como letras na tela.

Três pequenos indicadores que podem causar problemas grandes.

Encoding

Encoding define como caracteres são representados em bytes. UTF-8 é extremamente comum em desenvolvimento web. Caracteres estranhos como acentos quebrados podem envolver codificação.

Fim de linha

CRLF e LF são convenções de quebra de linha. Mudanças de uma convenção para outra podem fazer Git enxergar muitas linhas como alteradas.

Language Mode

Controla como o editor interpreta o arquivo. Se um arquivo .js estiver como Plain Text, você pode perder destaque e recursos inteligentes.

Quase ninguém explica: o conteúdo “parece igual” visualmente, mas bytes e finais de linha podem ser diferentes. Ferramentas de versionamento percebem essas diferenças.

15. Extensões: como instalar sem bagunçar seu ambiente

Extensões adicionam linguagens, formatadores, debuggers, temas e integrações.

Antes de instalar, pergunte:

  1. Qual problema ela resolve?
  2. O VS Code já faz isso?
  3. Quem publicou?
  4. Ela parece confiável e mantida?
  5. É necessária para este curso/projeto?
Evite listas de “30 extensões obrigatórias”. Iniciantes aprendem melhor com um ambiente previsível.
Diagnóstico avançado, mas simples: se um comportamento estranho apareceu, desabilitar temporariamente extensões ou testar um perfil limpo pode indicar se a causa está em uma extensão.

16. Workspace Trust e Restricted Mode

Esse aviso não existe para incomodar. Ele existe porque projetos podem conter coisas executáveis.

Um workspace pode incluir tasks, configurações, scripts e integrações capazes de executar ações. Em Restricted Mode, vários recursos ficam limitados até que você confie na origem.

Projeto aleatório baixado da internet? Não clique automaticamente em “Trust”. Leia o README, estrutura e scripts primeiro.

Workspace Trust não torna uma extensão desconhecida automaticamente segura. Extensões também executam código e devem vir de fontes confiáveis.

17. Busca e navegação em projetos

Em projetos maiores, procurar arquivo por arquivo deixa de funcionar.

  • Ctrl+P: abre arquivo pelo nome.
  • Ctrl+F: busca no arquivo atual.
  • Ctrl+Shift+F: busca em todo o workspace.
  • Go to Definition: navega para definição.
  • References: mostra onde um símbolo é usado, quando suportado.
  • Breadcrumbs: ajuda a entender a posição no arquivo/projeto.
Treino: encontre uma função pelo nome usando busca global, depois compare com procurar manualmente no Explorer.

18. Grupos de editor, split e organização da tela

Você pode abrir arquivos lado a lado.

Um caso simples: HTML à esquerda e CSS à direita. Outro: código de um lado e teste do outro. Use split para reduzir troca de contexto.

Mais painéis nem sempre significam mais produtividade. Se cada editor fica pequeno demais, a divisão atrapalha.

O terminal também pode ser movido e dividido. Aprender a reorganizar a tela ajuda muito em notebooks e monitores pequenos.

19. Source Control: o Git visto pelo VS Code

Repositório e Staging Area: o repositório é a estrutura usada pelo Git para acompanhar histórico. Pense no fluxo Working Tree → Staging Area → Commit: você altera arquivos, escolhe quais mudanças entram no próximo registro e então cria o commit.

O VS Code possui interface integrada de controle de versão, mas usa a instalação de Git do computador.

Git ≠ GitHub. Git registra versões. GitHub é uma plataforma de hospedagem e colaboração.

  • Changes: arquivos alterados.
  • Staged Changes: mudanças selecionadas para o próximo commit.
  • Commit: registro de um conjunto de mudanças.
  • Branch: linha de trabalho atual.
Importante: usar a interface gráfica e usar comandos no terminal manipula o mesmo repositório. Você pode aprender os dois aos poucos.

20. Run and Debug: observar o programa por dentro

Processo e Call Stack: um programa em execução existe como um processo no sistema. A Call Stack acompanha a cadeia de chamadas de funções e ajuda a responder “como a execução chegou até aqui?”.

Executar é obter resultado. Depurar é investigar a execução.

  • Breakpoint: ponto onde a execução pausa.
  • Variables: valores disponíveis naquele momento.
  • Call Stack: cadeia de chamadas que levou até ali.
  • Step Over: avança uma etapa sem entrar em determinada chamada.
  • Step Into: entra na chamada quando possível.
Logs não substituem debugger. console.log é útil, mas breakpoint permite congelar o estado e investigar variáveis no momento exato.

21. Tasks: automatizando comandos repetitivos

Automação: transformar uma rotina manual repetitiva em uma ação executável de forma consistente. Uma Task normalmente organiza comandos que também poderiam ser executados no terminal.

Tasks permitem ensinar ao VS Code como executar rotinas frequentes do projeto.

Podem representar build, testes, geração de arquivos ou outros comandos. Em projetos reais, isso reduz trabalho repetitivo.

Tasks podem executar comandos. Por isso também estão relacionadas a Workspace Trust.
Para iniciante: você não precisa criar tasks agora. Primeiro entenda terminal e comandos. Depois, automação passa a fazer sentido.

22. Profiles e Settings Sync

Profiles ajudam a separar ambientes diferentes dentro do VS Code.

Você pode ter um perfil “Curso Básico” com poucas extensões, outro para JavaScript/React e outro para Python.

Excelente para diagnóstico: um perfil limpo é útil para comparar comportamentos e descobrir se um problema vem de configuração ou extensão.

Settings Sync pode sincronizar preferências entre dispositivos quando configurado.

23. “Perdi meu código”: investigação antes do pânico

Muitas vezes o código não foi perdido; o contexto mudou.

  1. Você fechou o arquivo ou apagou?
  2. Abriu outra pasta?
  3. A aba estava em preview?
  4. O Explorer está filtrando ou ocultando algo?
  5. Undo recupera a alteração?
  6. Git tem uma versão anterior?
  7. Timeline/histórico disponível mostra versões?
Salvamento, Undo e Git são camadas diferentes. Git não substitui salvar; Undo não substitui versionamento.

24. Método para interpretar erros no VS Code

Não tente resolver erros olhando apenas a última linha.

  1. Onde apareceu? Terminal, Problems, navegador, Debug Console?
  2. Quem gerou? JavaScript, Node, Git, extensão, sistema?
  3. Qual arquivo? Há caminho e número de linha?
  4. Qual é a primeira mensagem importante? Uma falha inicial pode gerar várias mensagens depois.
  5. O erro se repete em um projeto mínimo? Isolar o problema ajuda.
ReferenceError: exemplo is not defined
    at app.js:15:3

Leia como: tipo do erro → mensagem → arquivo → linha/coluna. Essa disciplina é mais importante do que decorar soluções.

Hábito excelente: antes de pesquisar o erro inteiro, tente explicar com suas palavras o que a mensagem está dizendo.

25. Hábitos profissionais para aprender cedo

  • Abra a pasta correta do projeto.
  • Confirme o diretório atual do terminal.
  • Use poucas extensões e entenda cada uma.
  • Leia a Status Bar.
  • Use a Command Palette para descobrir recursos.
  • Faça mudanças pequenas e teste.
  • Leia mensagens de erro por origem, arquivo e linha.
  • Não confunda VS Code com linguagem, runtime ou Git.
  • Não execute comandos desconhecidos.
  • Use Git cedo, mesmo em projetos pequenos.
Meta final: você não precisa saber todos os botões. Deve conseguir se orientar, encontrar recursos, diagnosticar a camada do problema e trabalhar com confiança.
